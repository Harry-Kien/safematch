Framework proposal · Cyber security · 2026

Know who is really on the other side.

Dating apps in Vietnam can tell you a profile exists. They cannot tell you a person does. SafeMatch is a proposed safety layer that binds every profile to a verified national ID, watches for fraud patterns on the handset itself, and gives a victim one route to the cyber security authorities — with the evidence already attached.

Section 01 · The problem

A profile costs nothing to fake.

Romance fraud works because the platform never establishes who is typing. A scammer needs a stolen photo and an email address. The victim needs months to realise, and by the time they go to the police the account is gone and so is the evidence.

Section 02 · Controls

Four controls, three points in the timeline.

Group A runs once, at sign-up. Group B runs continuously while two people are talking. Group C runs only when something has already gone wrong. Each control is deliberately narrow — a control that tries to do everything is a control nobody can audit.

A.1 At sign-up · Identity

National ID capture

The applicant photographs both sides of their citizen ID card. The app reads the chip over NFC where the handset supports it, falls back to the printed QR where it does not, and checks the document against the issuing authority: is it real, is it current, has it been reported lost.

Control note Chip read is authoritative. A photograph alone is treated as unverified and routed to manual review.
A.2 At sign-up · Biometric

Face match and liveness

A short selfie capture is compared against the portrait held on the ID chip. Three randomised challenges — a blink, a slow head turn, a spoken digit sequence — establish that a live person is present, not a printed photo, a screen recording, or a synthetic video feed.

Control note Match threshold 0.82. Challenges are chosen at capture time so a recording cannot be prepared in advance.
B.1 While chatting · Behaviour

On-device scam detection

A small model runs inside the app, on the handset, and scores the conversation against known fraud patterns: pushing the chat to another platform, investment or crypto links, urgent money requests, a portrait that reverse-searches to somebody else. The user sees a warning before the money moves, not after.

Control note Inference is local. Only the resulting signal codes leave the device — never message text, and only if the user reports.
C.1 After harm · Escalation

Reporting to authorities

One action files a case with the cyber security unit. The report arrives with the flagged messages, the counterparty's verification status, and the transfer details already attached, so an officer is not starting from a blank form. The victim gets a case number and can follow its status.

Control note Evidence is released only on the user's explicit action. Nothing is forwarded automatically.

Section 03 · Sequence

What a user actually does.

Five steps, in order. The first three happen once and take under ninety seconds. The last two only matter if something goes wrong — and that is exactly when a person has the least patience for paperwork.

Step 01

Scan the ID card

User · 25 seconds

Front, back, then hold the card to the back of the phone for the chip read. The app extracts the fields and shows them for confirmation before anything is submitted.

Step 02

Prove you are present

User · 30 seconds

The selfie capture runs the three liveness challenges and compares the result with the portrait from the chip. A failed match does not block the account — it blocks the badge.

Step 03

Carry the verified badge

Platform · immediate

The profile shows a badge, not an ID number. Other users learn that a real, checked person is behind the account and nothing more than that.

Step 04

Get warned in the moment

Device · continuous

If the conversation starts matching fraud patterns, the app says so in plain language, in the chat, while the person can still act on it.

Step 05

File and follow the case

User → Authority

The report is pre-filled from what the app already holds. The user confirms what to include, submits, and receives a case number with a status they can check.

Section 04 · Architecture

Where each piece of data lives.

The design question is not what the system can collect. It is what it can be built to never hold. Behaviour analysis stays on the handset; the servers hold a verification result and, only after a report, a case file.

Zone 1 — Handset Runs inside the dating app
Dating app Host application, unmodified UI
SafeMatch SDK Capture, chip read, challenge flow
Risk engine Local model · message text never leaves

Leaves this zone Signed ID attestation · face match score · signal codes

Zone 2 — Verification service Operated under licence, audited
Document authority check Is the ID real, current, not reported lost
Badge issuer Issues a verified badge, not an identity
Retention job Biometric template destroyed after match

Leaves this zone Badge status only · true or false, plus an expiry date

Zone 3 — Authority console Cyber security unit
Case intake Opened only by a user-submitted report
Investigator workspace Evidence bundle, transfer trail, linked cases
Status channel Writes progress back to the reporting user

Access rule Every read of a case file is logged and attributable

Section 05 · Safeguards

The limits are part of the design.

A system that reads national ID cards and watches conversations has to say plainly what it will not do. These constraints are written as requirements, not intentions — each one can be tested.

§1

Analysis stays on the device

Conversation text is scored locally and is never transmitted for analysis. If the network is off, the risk engine still works.

§2

The badge reveals a status, not a name

Other users see that a person passed verification. They never see the ID number, the date of birth, or the address behind it.

§3

Biometrics are matched, then destroyed

The selfie and the derived template are deleted once the match completes. Nothing is retained to build a face database against.

§4

Evidence moves only when the user says so

No conversation is forwarded to any authority without an explicit report. There is no silent channel from the app to the console.

§5

A flag is a warning, not a verdict

The risk score warns the user. It cannot suspend an account on its own, and an accused user can see and contest what was flagged.

§6

Every access is on the record

Case files carry an append-only audit log. An independent reviewer can ask who opened a file, when, and under which case.

Section 06 · Questions

Fair objections.

The model that scores a conversation runs on your phone, and the text stays there. What can leave the device is a set of signal codes — for example "off-platform request" — and even those only travel if you file a report. No person at the platform or at an authority can open your chat history because you were flagged.

You keep your account and you keep using the app. You do not get the badge, and other users can choose to filter their matches to verified profiles only. Verification is a signal users can act on, not a gate the state puts in front of a consumer service.

Not reliably, and that is the honest answer — no liveness system is permanently safe against generated video. The design assumes attackers improve: challenges are randomised at capture time so a clip cannot be prepared in advance, the result is bound to the chip portrait rather than to a self-supplied photo, and a badge expires after twelve months so the check has to be repeated against whatever the detection state of the art is then.

The verification service checks the document and returns a yes or no with an expiry date. The dating platform receives that answer and stores nothing else. Your ID number is not handed to the app, and it is not shown to anyone you match with.
